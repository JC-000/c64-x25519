## A1 — `fe25519_mul_a24` byte-31 carry-out (fixed; catalogue L32)

`fe25519_mul_a24` computes `121665·a = hi·2^256 + lo` (`hi = fe_wide[32..34]
< 121665`, `lo = fe_wide[0..31]`), then folds `38·hi` (`2^256 ≡ 38 mod p`)
into `lo` through three carry-threaded stages and a final unconditional
ripple over bytes 4..31. `38·hi < 2^23`, so `lo + 38·hi < 2^256 + 2^23`
wraps 2^256 at most once — but it *can* wrap, because `lo` is an
arbitrary 256-bit residue. The ripple's byte-31 carry-out was dropped, so
whenever the sum reached 2^256 the result was short by exactly 38.
`fe25519_reduce_final` cannot repair a value that is wrong mod p.

Reach: ~5.8e5 canonical `a < p` (those with `lo` within 2^23 of 2^256)
and **every** `a ∈ (2p, 2^256)` — inputs that `fe25519_mul`/`sqr` do
produce (see A2). The RFC 7748 vectors and every random differential
case had missed them.

The banner's magnitude argument ("total reduction adds ≤ 19,418 … plus
the original fe_wide value < 2^256") bounded the addends, not the sum,
and the 19,418 was the un-weighted byte sum rather than the positional
`38·hi < 2^23`.

### Fix (`src/fe25519.s`, `fe25519_mul_a24`, after `@final_ripple`)

```
        lda #0
        adc #0                 ; A = C (no branch on the secret carry)
        tay
        lda mul38_lo_tab,y     ; Y in {0,1}: 0 or 38
        clc
        adc fe_wide
        sta fe_wide
        ldx #1
        ldy #31
@fold_ripple:
        lda fe_wide,x
        adc #0
        sta fe_wide,x
        inx
        dey
        bne @fold_ripple
```

The second fold cannot overflow: with C=1 the wrapped value is < 2^23,
so +38 stays far below 2^256; with C=0 nothing is added. Its byte-31
carry-out is always 0 and is dropped legitimately.

CT: no new branch; the only data-dependent index is Y ∈ {0,1} into a
256-byte table (no page-cross variance); the ripple is the same
fixed-length unconditional chain as `@final_ripple`. Measured:

- `tools/test_ct_mul_a24_cycles.py`: **0.00000 jif spread** (0.515 jif/call,
  all 12 inputs).
- `tools/test_ct_ladder_cycles.py`: **0-cycle spread** across every
  scalarmult class (`k ∈ {clamp(00*32), clamp(FF*32), clamp(55*32),
  clamp(random)} × u ∈ {9, 0, 1, p−1, random}`, all 262,456,952 cycles),
  and 0-cycle spread on add / sub / reduce_final / inv.

After the fix `tools/test_fe_adversarial_bigint.py` reports
`PASS: 93 field-op calls checked`.

## A2 — Inv3 bound was "≤ 2p"; the truth is < 2^256 = 2p + 38

Measured: `(2p−1)²` reduces raw to `2p+1`; the `(2p−i)(2p−j)` search
maximum reaches `2p+37 = 2^256−1`. Correctness never depended on the
false bound:

1. `fe25519_reduce_final`'s two masked sub-p iterations cover any
   `R < 3p` (iter 1 leaves `R < p+38`, iter 2 leaves `R < 38`).
2. `fe25519_add` with one canonical partner: sum `< 2^256 + p`, so the
   single masked sub-p (borrow wraps mod 2^256) returns `sum` or
   `sum − p` — correct mod p and < 2^256, which is all the next
   mul/sqr/mul_a24 need (canonical only when `sum − p < p`; the
   `x25519.s` W4 comments now say so).
3. `fe25519_sub` keeps the non-canonical operand on `src1`.
4. `fe25519_mul_a24` was the one consumer that did not tolerate an input
   above 2p — that is A1.

Corrected in `docs/CT_ANALYSIS.md` (L27f, L29d, Phase-7 mechanism text,
new A2 note), `src/fe25519.s` (`fe25519_reduce_final` banner),
`src/x25519.s` (both W4 pruning comments), and
`tools/test_fe_reduce_wide_bound.py` (now asserts `≤ 2p+37`).

## A3 — `tools/test_rfc7748_iterated.py` had never passed

- `RFC7748_ITER1_EXPECTED_HEX` tail was `…e11196e8edcc4f1351d2cea3a6c4c6cd87bc8c0a48f2c1ee`;
  RFC 7748 §5.2 is `422c8e7a6227d7bca1350b3e2bb7279f7897b87bb6854b783c60e80311ae3079`.
  Its own pyca sanity gate rejected the literal before any ladder ran.
- Docstring claimed the library clamps `x25_scalar` internally. It does
  not (`src/x25519.inc`: caller clamps; only `x25519_base` clamps). The
  test now clamps `k` caller-side.
- Gated on `--slow` behind a stale "~100 min per ladder" (measured
  18–26 s under VICE warp), and absent from `make test-slow`.

## A4 — `tools/test_x25519_edge_u.py` had never passed

pyca/OpenSSL raises `ValueError("Error computing shared key")` on an
all-zero shared secret (RFC 7748 §6.1 MAY-check); the test propagated it
and died on its first case (`u = 0`). It now treats that ValueError as
"expected all-zero output" per §6.1 and asserts the library returns 32
zero bytes. Same stale gating as A3.
